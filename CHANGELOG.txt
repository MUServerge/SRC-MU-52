- Client renderer Phase 10: added capability-selected BMD bone transport to
  the single active VBO Model shader. The same Model.vs source is compiled with a
  validated std140 9,600-byte BoneBlock when OpenGL 3.1/ARB UBO support, required
  entry points, binding capacity, linked block size and buffer allocation pass;
  otherwise it recompiles through the previous uniform-array contract, with the
  legacy BMD draw remaining the final fallback. CShaderGL now owns and releases
  the UBO under the current context, BMD rejects failed palette uploads before
  drawing, and RenderProfiler distinguishes UBO versus uniform-array palette
  uploads and UBO binds. VBO eligibility, shader lighting/material math, draw
  order, CPU transforms, gameplay timing and packets are unchanged. Static source
  verification only; Windows build, visual parity and performance measurements
  remain pending. Runtime validation can force `MU_BONE_TRANSPORT=ubo`,
  `uniform` or `legacy`; the variable is absent by default.

- Client renderer Phase 9: removed dormant shader/VBO experiments from the
  production runtime after resolving their intent and preserving the useful
  architecture as an explicit migration specification. The client now owns only
  the active Terrain, Character and VBO Model programs; removed duplicate Default,
  unowned Glow/Colorize/text prototypes, the obsolete dynamic VBO adapter and the
  unreachable per-material VBO programs. Chrome/Metal/Oil legacy UV equations and
  the validated std140 bone-palette concept are documented for future integration
  into the single active BMD technique. Active VBO eligibility, legacy fallback,
  render order, game timing, packets and assets used by current draws are unchanged.
  Static source review only; Windows build and runtime performance/visual validation
  remain pending.

- Client renderer Phase 8: consolidated active shader file loading through
  CShaderScene and changed program creation to demand-driven ownership. Terrain,
  Character and the currently eligible VBO Model technique are preloaded; Default,
  Glow, Colorize and the ten gated VBO material variants remain available but are
  compiled only on their first real request. Failed lazy loads are remembered so
  render loops do not retry file I/O or compilation every frame. Removed startup
  compilation of CShaderGL's duplicate legacy Shaders/shader.vs/fs program; its
  unreferenced adapter retains the existing client-array fallback. Shader assets,
  VBO eligibility, draw order, material formulas, gameplay and GL context behavior
  are unchanged. Static review only; Windows build/runtime validation remains
  pending. (CShaderScene.cpp/.h, CShaderGL.cpp/.h)

- Client renderer Phase 7: audited the uploaded Client/Shaders,
  Client/Data/Effect/VBO and Client/Data/Effect/shader GLSL assets against the
  active loaders, then tightened BMD VBO creation validation. Models with an
  invalid bone count, non-triangle/quad polygon, invalid vertex/normal/UV index,
  invalid vertex or normal bone, or a vertex/normal split across different bones
  now keep VAO == 0 and use the existing legacy renderer. The VBO shader contract
  exposes one bone attribute for both position and normal, so split-node corners
  cannot be represented without changing output. Removed the silent bone-zero
  substitution. No shader asset, draw order, gameplay or file format changed;
  rejected meshes reuse the unchanged legacy fallback. Static review only;
  Windows build/runtime validation
  remains pending. (ZzzBMD.cpp)

- Client renderer Phase 6: added runtime introspection for every linked VBO
  program's active u_Bones vec4 array and compared its declared component use
  with GL_MAX_VERTEX_UNIFORM_COMPONENTS. Programs with a missing/incompatible
  bone contract are deleted and disabled; models with null, zero, oversized or
  over-capacity bone data return to the existing CPU/legacy draw before any VBO
  bind/upload. Added capability diagnostics and a profiler rejection counter.
  Shader files, bone transport format, gameplay and legacy output are unchanged.
  Static review only; Windows build/runtime validation remains pending.
  (CShaderGL.cpp/.h, ZzzBMD.cpp, Winmain.cpp, RenderProfiler.cpp/.h)

- Client renderer Phase 5: reused uView/uProj uniform values once per VBO program
  inside the Phase 4 per-RenderBody matrix snapshot. Bone, light, material and
  sampler uniforms remain on their original per-mesh update path. Tracking is a
  fixed 16-program array with no heap allocation; capacity exhaustion falls back
  to the original matrix uploads. Direct RenderMesh calls, shader selection,
  draw order and visual intent are unchanged. Static review only; Windows
  build/runtime validation and measured comparison remain pending.
  (ZzzBMD.cpp/.h)

- Client renderer Phase 4: scoped fixed-function model-view/projection snapshots
  to one BMD::RenderBody mesh loop. The first successful VBO mesh captures the
  exact current matrices and sibling meshes reuse them; direct RenderMesh calls
  retain the original per-draw queries. This avoids unsafe frame-global caching
  and preserves temporary NewUI/inventory preview cameras, matrix uploads, draw
  order and the legacy fallback. Static review only; Windows build/runtime
  validation and measured performance comparison remain pending.
  (ZzzBMD.cpp/.h)

- Client renderer Phase 3: added a bounded, allocation-free per-program uniform
  location cache under the authoritative CShaderScene owner, including negative
  lookup caching and explicit invalidation before program deletion. Active
  CShaderGL scene, legacy and VBO programs now share one compile/link/error path;
  the non-SHADER_PIPELINE compiler remains as the compatibility fallback. Shader
  files, uniforms uploaded, material selection, draw order and visual intent are
  unchanged. Static review only; Windows build/runtime validation is pending.
  (CShaderScene.cpp/.h, CShaderGL.cpp/.h)

- Client renderer Phase 2: centralized all active GLSL program binding and
  nested restoration through CShaderScene's authoritative GL_CURRENT_PROGRAM
  tracker. CShaderGL now uses adapters for legacy/VBO programs and no longer
  keeps an independent stale current-program cache. Scene techniques, shader
  sources, material selection and legacy fallback are unchanged. Static review
  only; Windows build and runtime visual/state validation remain pending.
  (CShaderScene.cpp/.h, CShaderGL.cpp/.h, ZzzBMD.cpp)

- Client renderer Phase 1: made shutdown idempotent and moved ImGui, model,
  texture and shader teardown ahead of WGL context destruction. BMD::Release now
  deletes and clears every mesh-owned VAO/VBO/EBO while a context is current;

  (WINHANDLE.cpp, CShaderGL.cpp/.h, ZzzBMD.cpp)

- Client: smoothed the free-camera horizontal rotation (CGMCameraWorld::RotateInNearFar).
  Middle-mouse yaw was a flat +/-5 deg per frame keyed only on cursor direction - not
  proportional to mouse movement, no momentum, framerate-dependent and steppy. Replaced
  it with a momentum model (inspired by the community SmoothCamera): the real mouse delta
  is accumulated into the existing rotateVelocityX and eased out every frame with the
  framerate-independent FPS_ANIMATION_FACTOR, so turns are proportional and glide to a
  smooth stop. Zoom (already eased) and the vertical up/down pitch (SetAngleY) are left
  unchanged. Sensitivity/settle are tunable via ROTATE_SENSITIVITY / ROTATE_SMOOTH.
  Pending build+run.

  fullscreen splash it must cover the whole window at any resolution AND ScreenType.
  The original double-scaled (pre-mul by ScreenW/800 + RenderBitmap's own g_fScreenRate
  scale); simply removing the pre-scale then under-filled, because RenderBitmap's
  g_fScreenRate does NOT map the 640x480 base to the full window on ScreenType 1
  (aspect-lock) or 2 (fixed rate) - leaving black margins (right/bottom). Now the art
  is scaled by the ACTUAL window size (WindowWidth/640, WindowHeight/480) and drawn
  with RenderBitmap Scale/StartScale = false (raw window pixels), so it fills the whole
  GL surface on every ScreenType. Back01/Back02 now render as the left/right window
  halves (no crop/black bar). Gauge bar untouched - it keys off the real window size
  too (ScreenW/800), so it stays aligned via the 640/800 == 480/600 == 0.8 equivalence.
